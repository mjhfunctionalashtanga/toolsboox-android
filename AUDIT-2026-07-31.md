# Ledgable — audit, 2026-07-31

Five parallel audits over both forks (sync/merge parity, Android data-loss, iOS data-loss,
adversarial review of the day's own commits, security/hygiene), findings then hand-verified at the
cited lines before being written down here. Covers iOS `correspondence` and Android
`punchlist-2026-07-26` as of the buttons-on-top build (`1.06.06-01` / build 39).

**The merge core is sound.** The deleted-page-key port was checked guard-by-guard and is
semantically exact; every union rule, tombstone normalization, and clock stamp matches across the
forks. Day-file saves are atomic on both platforms; Android's sync has the mid-merge pen-up guard,
watermark discipline, and truncated-download refusals all working as documented. The failures below
live around that core, not in it.

## Critical — ink loss with propagation

1. **iOS sync writes back a stale snapshot of the day** (`CalendarSyncEngine.swift` `mergeBothSides`:
   local read at :91, network await, merged write at :125 with no re-check). A pen-up save landing
   during the download window is overwritten locally AND pushed, so every device converges on the
   loss, tombstones included — which can also resurrect erased ink. Android handles exactly this
   (`CalendarWebDavSyncService.kt:242-245` re-checks `lastModified` and defers). **Fix: port
   Android's guard — re-stat the file before the local write; on mismatch, skip and leave the
   watermark back.** VERIFIED.

2. **iOS reader/book ink has no background flush** (`Bookshelf.swift:733` saves only on
   `.onDisappear`/pane toggles; no `scenePhase` handler, no pen-up debounce — ink saves on *erase*
   only). The day page flushes on background (`PlannerShell.swift:729-736`) precisely because iOS
   kills backgrounded apps; the reader gets none of that. Backgrounding mid-note loses everything
   since the pane opened. Same for the three other surfaces routed through `BookNotesStore`.

3. **`BookNotesStore` (iOS) is the weakest store in either fork**: non-atomic write of the whole-book
   ink map (`BookNotesStore.swift:80`, no `.atomic` — every sibling store uses it); truncated file
   reads as "no notes" then the next save writes a one-key map over it and *pushes it*; sync merges
   per-key by wholesale replacement (`:114-119`) so two devices annotating one chapter lose the
   smaller edit on both sides; a locally-erased page resurrects from remote (absence can't express
   deletion — no headstones here). VERIFIED (non-atomic + merge rule read directly).

## High

4. **Document-deletion headstones are immortal** (`LedgerDocumentTombstones.kt`: `forget` edits only
   the local file; `merge` at :97-106 is a pure union with remote). Delete a Write/Grid/Jot daily
   document, later re-title that same day: the name shows, then vanishes on every device, forever —
   the remote headstone re-unions in and strips the recreated row. The `merge` docstring's "there is
   no conflict two devices can have about a document they both agree is gone" misses
   rename-after-delete. **Fix needs a lifted-headstone record (e.g. a `revived.json` or per-id
   epoch) that subtracts on merge — plain forget can never win a union.** VERIFIED.

5. **Month/Week/Quarter/Year/Pattern ink: non-atomic saves, no corrupt-load guard, no sync, no
   backup** (`CalendarMonthService.kt:155` and twins — direct `PrintWriter` to the final name; loads
   throw on truncation). Day pages got the temp+`checkError`+`ATOMIC_MOVE` hardening; these five
   siblings did not, and `DAY_FILE_REGEX` means there is no remote copy to recover from. iOS's
   `PageStore.swift:18` is the same story on the other side.

6. **A day that fails to load renders blank and the first stroke saves over it**
   (`CalendarDayService.load` → null → fresh empty day → pen-up persists it). The code's own comment
   names the danger; nothing acts on it. The WebDAV merge refuses unparseable sides so a synced day
   is recoverable from another device — an unsynced or Drive-only day is not. **Fix: a read-only
   "couldn't load — not saving" mode when load returned null for a file that exists.**

7. **iOS names-backup import lets stale headstones kill live rows and pushes the kill**
   (`LedgerSettingsBackup.swift:386-410` folds imported headstones in unconditionally; Android
   (`NamesBackup.kt:412-421`) explicitly refuses a headstone against a live row. Same merge-id
   namespace on both sides, so the daily write|/grid|/sketch| keys really collide. **Fix: adopt
   Android's live-row guard on import.**

8. **Feed article HTML runs unsanitized, with JS on, in a WebView whose origin is the feed entry's
   own URL** (`FeedArticleFragment.kt:67,409,451`; also `FeedsFragment.kt:1047,1367`) — and the
   global cookie jar holds logged-in WP sessions (`SiteWebFragment`). One malicious feed item with
   `url` pointed at a session origin can read those cookies. **Fix: Jsoup-allowlist the body and use
   a fixed sentinel base URL.** VERIFIED.

9. **The settings/ledger backup writes every secret as cleartext JSON** — Android
   `CalendarSettingsFragment.kt:579-585` stages `ledger-settings.json` in cache and never deletes
   it, and embeds it in the export zip; iOS `SyncSettingsView.swift:354-356` mirrors it. WebDAV
   password, both AI keys, Miniflux token, site passwords, mail passwords — decrypted into a file
   that lands in Downloads/iCloud. **Fix: delete the staged file after share; passphrase-encrypt or
   opt-in the secrets section.**

## Medium

10. **iOS sync planner compares the day JSON's own `updated` against the server's `getlastmodified`**
    (`SyncPlanner.swift:54,67`; remote stamp minted from HTTP date at `SyncProvider.swift:268-270`).
    Two clocks, two meanings — Android keeps two watermarks precisely to avoid this. Costs: every
    pushed file re-downloads on every pass forever (server mtime > content stamp), and an exact tie
    stalls convergence for that day. VERIFIED.

11. **iOS output is not byte-deterministic**, so the stated byte-identity invariant can't hold:
    stroke-map key order is seeded per process (`.sortedKeys` only applies in the prettyPrinted
    branch of `JSONCoder.swift`); top-level field order differs from Moshi's (the comment in
    `CalendarDay.swift:5-6` claiming otherwise is wrong); UUIDs uppercase vs lowercase; absent-vs-""
    optionals flip across saves. Convergence still holds (both sides compare parsed content, and
    Android's string-compare only causes extra rewrites, not ping-pong) — but it's permanent churn
    and a trap for any future byte-level comparison.

12. **Sidecar stores race their own sync threads** (unbounded `Thread{}` per call in
    `LedgerSidecarSync.kt:200-203`; every store is whole-file read-modify-write with no `DayLocks`
    equivalent). Two quick edits can lose the second one on disk and push the loss. Same shape on
    iOS (`BookNotesStore.sync` in `Task.detached`). Also: most Android sidecar files are still
    plain `writeText` (non-atomic) with readers that treat corruption as empty — self-healing only
    where WebDAV is configured.

13. **Intake Later-list removals are substring tombstones applied to every line of every day**
    (`IntakePageStore.kt:100-110`, `LaterRemovals` never expires). Removing a bare-domain link can
    silently delete every filed line containing that domain, across the 120-day window, propagated.

14. **`AndroidReaderBridge` stays attached if the reader WebView navigates off `ledger.reader`**
    (`ReaderFragment.kt:113`, no `shouldOverrideUrlLoading`). An EPUB with an external link can land
    on a page that forges highlight/relocate messages into the day file. **Fix: send non-reader
    URLs to an external intent.**

15. **`allowBackup="true"` with no backup rules** (`AndroidManifest.xml:16`) — the whole ledger and
    the staged secrets file ride Google Auto Backup; restored `EncryptedSharedPreferences` throw on
    a new device anyway. `PanelWebhook` keys additionally sit in plain prefs
    (`PanelWebhook.kt:35/:46`). iOS keeps several tokens (`opds_pass`, `bl_pass`, `mf_token`,
    `tts_openai_key`, …) in UserDefaults instead of Keychain (`LedgerSettingsBackup.swift:14-16`
    guards only four keys).

## Minor / recorded

- `doneAnywhere` computed pre-filter (Kotlin) vs post-filter (Swift) — no observable divergence
  today; align when touched. Tombstone sort collation differs only for non-ASCII ids nothing mints.
- Neither fork ever deletes superseded `-v1.json` files; iOS re-uploads stampless v1 files every
  pass.
- Android names-import rewrites unparseable local rows out of `pages.json` (`NamesBackup.kt:389-400`)
  — the read-side "skip" rationale doesn't justify a write-side delete.
- Registry renames are local-wins with no row clock — cross-device rename durability is
  last-to-sync. Deliberate, but worth an `updatedAt` eventually.
- The `renameTo` fallback (`f.delete(); tmp.renameTo(f)`) deletes the good copy first in five
  stores; `Files.move(REPLACE_EXISTING)` is already the fixed pattern in `CalendarDayService`.
- `keystore.jks` in the public repo's history is upstream's own (already public in gaborauth's
  repo), not ours; current tree clean, no other secrets in history. `INTAKE_KEY` correctly out of
  tree but is a bearer secret compiled into any distributed APK — rotate on release, scope
  server-side.
- Element-only pages: deleting the last card off a one-sided page can drop the page key (the
  `erasedPages` arm fires with zero strokes) — identical on both forks, untested on both.
  Parity, not divergence; pin it in tests when touched.
- Two dialogs call `dialog.show()` instead of `showModal` (skips e-ink refresh hooks):
  `BookNotesPanel`, `LedgerItemsFragment`. Pre-existing.

## Also cleared by the audit, for the record

The RosterFragment "Save to CRM" button had NEVER worked — `showModal` overwrites the
`setOnShowListener` that wired it, so it silently dismissed without saving since the day it was
written. Today's buttons-on-top rewrite fixed it by accident. No other dialog in the tree combines
`setOnShowListener` with `showModal`. Deep links, share handler, TLS handling, release logging, mail
WebView, widget receivers: all clean. Day-save atomicity, stroke-id stability, erase tombstones,
the pen-up mid-merge guard (Android), truncated-download refusals: all confirmed working.

## Fixed same day, round two (in `1.06.07-00` / iOS build 39)

Criticals 1-3, highs 4-5 and 7-9, and mediums 10, 12, 13, 14, and 15 are FIXED and shipped:
the iOS sync engine re-stats before writing (and syncFinished flushes the canvas first); reader
ink flushes on scenePhase with a pen-up debounce; BookNotesStore went atomic + quarantined +
tombstone-union-merged (with diffed stroke ids); headstones carry {d,r} epochs on both forks so
rename-after-delete finally wins; the five period services save atomically with quarantine (and
the delete-first rename fallback is gone everywhere); the names import guards live rows on iOS
and legacy headstones land at the dawn of time; feed HTML is jsoup-allowlisted on a sentinel
origin; the settings export passphrase-encrypts its secrets (AES-256-GCM/PBKDF2, cross-fork
envelope) and deletes its staged copy; the iOS planner runs two same-clock watermarks (11 new
tests); sidecar syncs are serialized on both platforms; Later-list tombstones match canonical
URLs; the reader WebView sends foreign URLs to the browser; backup rules exclude the prefs and
ledger tree, webhook keys moved to encrypted prefs, and eight iOS tokens moved to the Keychain.

Still open from this audit: item 6's read-only mode SHIPPED (Android); byte-identity across
forks remains parse-level only (iOS now at least self-deterministic via sorted keys); v1 file
cleanup; registry rename clocks; the residual same-page-open-on-both-devices book-note race
(now a propagated deletion rather than a silent overwrite — reload-on-merge is the roadmap fix);
`star_webhook_secret` still in UserDefaults; the element-only-page guard edge untested on both.
